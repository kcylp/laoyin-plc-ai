## 3.2　步超时监控

**id** `step-timeout`

### 名称/别名
**中文**：步超时监控 · 卡步检测 · 看步 · 步超时报警 · 流程监视
**英文**：Step Timeout Monitoring · Step Watchdog · Sequence Timeout

### 适用场景
与 3.1 配套。**每一步都必须有超时监控** —— 卡步了要报警，不能无声无息等一辈子。也用于单个动作的到位超时（气缸、阀、电机）。

### 梯形图逻辑描述

**方案 A：每步一个定时器（步数少时清晰）**

```
Network 1: 步 10 超时
  Eq([步号], 10)  →  T_Step10(IN)，PT = 步10超时值
  常开[T_Step10.Q]  →  SCoil[步10超时报警]、SCoil[有报警]、Move(0)→[首出步号]
Network 2: 步 20 超时（同构）
  Eq([步号], 20)  →  T_Step20(IN)，PT = 步20超时值
  …
```

**方案 B：共用一个定时器 + 按步号查表取 PT（步数多时推荐）**

```
Network 1: 步号变化 → 复位定时器并载入本步超时值
  Ne([步号], [步号_上周期]) → PBox → 线圈[步复位]
  常开[步复位] → RT（复位定时器）  ← ⚠️ RT 未在白名单，见下

  查表：Move([超时表[步号索引]]) → [当前步超时值]

Network 2: 共用定时器
  常开[步内运行中]  →  T_Step(IN)，PT = [当前步超时值]
  常开[T_Step.Q]    →  SCoil[卡步报警]，Move([步号]) → [卡步步号]

Network 3: 整循环超时（兜底）
  常开[循环运行中]  →  T_Cycle(IN)，PT = 整循环超时值
  常开[T_Cycle.Q]   →  SCoil[循环超时报警]
```

⚠️ **`-(RT)-`（复位定时器）与 `-(PT)-` 不在《技术底座》白名单**（全项目零实例）。方案 B 的"复位定时器"当前**只可人工编写**；可生成的变通做法是让定时器的 `IN` 断开一个扫描周期（用步号变化沿把 `IN` 拉低），这样 TON 自然复位 —— `PBox`、`Not`、`Contact`+`<Negated>` 都在白名单内。

**方案 A 全部可用白名单指令实现，是当前的可生成方案。**

### 变量表

| 名称建议 | 数据类型 | 方向/存储区 | 说明 |
|---|---|---|---|
| `步号` / `Step` | Int | DB | 见 3.1 |
| `步n超时定时` / `T_Step_n` | IEC_TIMER | FB→**Static** | 方案 A：每步一个 |
| `步超时定时` / `T_Step` | IEC_TIMER | FB→**Static** | 方案 B：共用 |
| `步n超时值` / `Step_n_Tmo` | **Time** | DB | 可现场调，每步一个 |
| `当前步超时值` / `Cur_Tmo` | Time | M / DB | 方案 B |
| `卡步报警` / `Alm_StepTmo` | Bool | M / DB | **锁存**（见 4.1） |
| `卡步步号` / `Tmo_Step` | Int | DB | 记录是哪一步卡的 —— **诊断的关键** |
| `循环超时定时` / `T_Cycle` | IEC_TIMER | FB→Static | |
| `循环超时报警` / `Alm_CycTmo` | Bool | M / DB | |
| `步实际用时` / `Step_n_ET` | Time | DB | 记录用，便于整定 |

**强烈建议记录 `卡步步号` 与各步 `实际用时`** —— 没有这两个数，现场只能看到"设备停了报卡步"，无从下手；有了这两个数，5 分钟就能定位。

### 参数与整定

| 参数 | 建议初值 | 范围 | 依据 |
|---|---|---|---|
| **单步超时** | 该步正常动作时间 × **2** | 该步正常时间 × **1.5–3** | 《整定值》2.5。**每一步都必须有** |
| 整循环超时 | Σ 各步正常时间 × **1.5** | — | 兜底，防某步反复重入（《整定值》2.5） |
| 气缸/执行机构到位超时 | 正常动作时间 × **2**，且 **≥ 1 s** | × 1.5–2，≥ 1 s | 留气压波动、油污增阻、低温余量（《整定值》2.4） |
| 回原点超时 | 正常回零时间 × **3**，且 **≥ 10 s** | — | 回零可能从最远点开始（《整定值》2.3） |

**「正常动作时间」的获得方式（《整定值》明确）**：**正常运行时记录各步实际用时**（把 `T_Step.ET` 在每步结束时存进 DB），跑够样本后按上表系数算超时值。气动机构则**现场手动打一次掐表**，不许算。

### 常见坑　⚠️【待老殷审】

- **超时时间取得太短** → 误报警。现场被误报警烦了会**把报警关掉**，那比没有报警更糟（《整定值》2.5 原话）。
- **超时时间取得太长** → 卡步半天没人知道，物料/工件报废。
- **只有整循环超时，没有单步超时** → 报"循环超时"但不知道卡在哪一步，排查靠猜。**每步都要有**。
- **不记录卡步步号** → 报警清除后信息丢失，无从追溯。
- 🔴 **运行中改超时 PT 无效** —— 官方 Table 7-19："**Changing PT has no effect while the timer runs.**"
  → 调超时值时看起来"改了没反应"，必须**先复位定时器**。**这是"改了设定值没反应"的头号根因，必须写进调试指引。**
- 🔴 **定时器线圈形式必须是 network 最后一条指令**（官方 p.184），因此取不到 Q/ET，要在下一个 network 读 `DB.timer.Q` / `.ET`。（`-(RT)-`/`-(PT)-` 相反，可放中间。）
- **共用定时器不在步变化时复位** → 上一步用掉的时间累计到下一步，导致提前误报。方案 B 必须在步号变化时复位。
- **PT 传负数** —— "**Negative PT values are set to zero**"，不报错，表现为"一进这步就报超时"。
- **报警不锁存** → 卡步条件消失（比如气缸终于到位了）报警自动清除，操作工什么都没看到，隐患被掩盖。**必须锁存**（见 4.1）。
- **超时后不停机** → 只报警不停，设备继续往下跑，可能撞机。**超时必须联锁停机**（除非工艺明确允许继续）。
- **FB 内定时器实例放 M 或全局 DB** → 多实例串味。**放 Static**。
- **每步一个定时器时步数很多** → 16 个线圈上限也可能撞到【本机 `BL_TOO_MANY_COILS`】：
  EN: `Too many coils in one network. A maximum of 16 parallel coils is allowed.` / ZH: `一个程序段中的线圈太多。最多允许有 16 个并联线圈。`
  → **拆 network**，不要往一个 network 里堆。

### 上机前必须确认　⚠️【待老殷审】

- [ ] **每一步都有超时监控**（逐步核对，不漏一步）
- [ ] 每步的超时值来自**实测的正常动作时间 × 系数**，不是占位值
- [ ] 各步**实际用时已记录**（正常运行跑够样本），并进了交付文档
- [ ] **卡步步号被记录**，且报警清除后仍可查（存进保持性 DB 或报警历史）
- [ ] 超时报警**已锁存**，需人工复位（见 4.1）
- [ ] 超时**联锁停机**（或已与甲方确认某些步允许继续）
- [ ] 调试人员知道**运行中改 PT 无效，要先复位定时器**（写进调试指引）
- [ ] 整循环超时已设，且大于各步超时之和
- [ ] FB 内定时器实例在 Static
- [ ] 若某 network 线圈接近 16 个：已拆分
- [ ] 全部超时值都进了交付文档整定值表（七列齐全），"已确认"列留空由现场签字

### 可生成性
**✅ 可自动生成**（方案 A：每步一个定时器）。`Eq`、`TON`、`Contact`、`Coil`、`SCoil`、`Move` 全在白名单。
⚠️ 方案 B 里的 `-(RT)-` 复位定时器**不在白名单**（零实例）—— 生成时改用"IN 断一周期"的变通实现，或告知用户手工加。
