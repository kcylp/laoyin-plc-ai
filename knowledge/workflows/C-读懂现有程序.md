## 这份手册解决什么问题

"读懂别人的程序"是工控现场最常见、也最没有方法论的活。多数人的做法是**打开 OB1 从第一个网络往下看**，看到第三个块就迷路了，因为：

- 变量名可能是拼音、可能是乱码、可能根本没注释；
- 逻辑分散在十几个块里，谁调谁看不出来；
- 真正决定设备动不动的那个位，往往在你没打开的那个块里被写了第二次。

**工作流 C 的核心纪律：自顶向下、先结构后细节、只读不写。** 先把"骨架 + 数据流"画出来，再决定要不要钻进某个网络。

**它还是工作流 B 的前置。** 不先读懂就改，就是拿客户的产线赌运气。

## 阶段 0 · 只读纪律（本工作流唯一的红线）

**本工作流全程禁止四类动作：**

| 禁止 | 为什么 |
|---|---|
| ❌ 写入任何块（`/api/tia/import`） | 读程序不需要写 |
| ❌ 编译（`CompileSoftware` / `CompileAndDiagnosePlc`） | 🥉 惯例：编译会改动块的编译状态与时间戳，客户的工程会"看起来被动过"。如果客户就是要你顺手编译，必须先明说并得到同意 |
| ❌ 保存 / 另存（`SaveProject` / `SaveAsProject`） | 会固化任何无意的改动，属 TASK-006 认定的危险操作 |
| ❌ 任何命中 `download\|delete\|remove\|force\|stop\|reset` 的工具 | 🥇 产品侧 `POST /api/tia/mcp/call` 对这些名字设了闸门，必须显式 `confirmed:true`。**读程序阶段一个都不该命中** |

**接活开场就要把这条说出去**：

> 这是**只读**分析，我不会往你的工程里写任何东西、不会编译、不会保存。你可以放心让我看。

### 0.1 三项前置确认

| # | 检查 | 手段 | 不过怎么办 |
|---|---|---|---|
| 0.1 | 博途已连接并挂接到目标工程 | `GET /api/tia/mcp/status` | 引导"连接博途" |
| 0.2 | **工程处于离线状态** | 若刚做过在线操作，先 `GoOffline` | 🥈 官方原文（`TraceTagCause` 工具说明）："block export needs the project OFFLINE in TIA — Openness cannot export blocks while it is connected online to the PLC." **在线状态下导不出块** |
| 0.3 | 是否存在**专有技术保护块** | 试导出即知 | 保护块读不到源码【本机 V21 · `Openness_Fbk_BlockLanguageNotSupported`】：`The block '{0}' is know-how-protected and cannot be exported.` / `块“{0}”设有专有技术保护，无法导出。` → **如实告知这部分是黑盒**，只能从它的接口和调用关系反推 |

## 阶段 1 · 采集：一次把料备齐（别边读边查）

**纪律：一次性把下面这批读完再开始分析。** 边读边查会把互斥队列（`enqueueTiaOp`）打得很碎，也容易漏。

| # | 读什么 | 产品通道 / MCP 工具 | 用来回答 |
|---|---|---|---|
| 1.1 | **软件树** | `GET /api/tia/mcp/software-tree` → `GetSoftwareTree` | 一共几个块？什么类型？什么语言？ |
| 1.2 | **块清单 + 分组层级** | `GetBlocksWithHierarchy` | 作者是怎么组织这个工程的（分组名往往就是他的架构意图） |
| 1.3 | **PLC 变量表** | 硬件面板 →「变量表列表」→ `POST /api/tia/mcp/tag-tables` → `GetPlcTagTables` | I/O 都接了什么？中间量叫什么？ |
| 1.4 | **PLC 数据类型（UDT）** | `GetTypes` / `GetTypeInfo` | 有没有自定义结构？（有 UDT 通常说明作者水平不低） |
| 1.5 | **工艺对象** | `GetTechnologyObjects` | 有几个轴？什么类型？（有轴 → 一定有 MC_* 调用） |
| 1.6 | **外部源文件** | `GetPlcExternalSources` | 有没有 SCL/STL 文本块？这些块的读法不同 |
| 1.7 | **监控表 / 强制表** | `GetPlcWatchTables` / `ExportPlcWatchTable` | 🥉 **被低估的金矿** —— 上一个工程师调试时盯的就是这几个变量，等于他留下的笔记 |
| 1.8 | **交叉引用** | `GetCrossReferences` | 谁调用谁、谁写了哪个位。工具自述 best-effort，**拿不到必须回退人工 F11** |
| 1.9 | **目标块源码** | 左树点块 →「解读」；右侧上下文面板 →「导出 S7DCL」 | 见阶段 2.3 |

⚠️ **同名块会挡住导出**（🥇 源码实读）：软件树里出现多个同名块时，`/api/tia/mcp/export-s7dcl` 返回 **409**：
> `检测到 N 个同名块"<名>"，批量导出工具无法按组路径唯一定位，已拒绝导出以避免下载错误内容`

这是产品有意的保护。读程序阶段遇到它，**本身就是一条重要发现**——写进理解笔记："工程里存在同名块，分组路径不同，接手时需消歧"。

## 阶段 2 · 自顶向下：OB → FC/FB → DB

### 2.1 第一层：先定"入口有几个"

在软件树里找出所有**组织块（OB）**。

🥉 **纪律：不要按记忆假定 OB 编号的含义，读软件树里实际存在的那些。** 同一个功能在不同项目里可能挂在不同的 OB 上；S7-1200 与 S7-1500 的可用 OB 类型也不同。**软件树里的名字与类型才是真值。**

对每个 OB 记三件事：
- 它是什么类型（主循环 / 启动 / 循环中断 / 硬件中断 / 故障处理）
- 它调用了哪些块（这就是骨架）
- 它自己有没有写业务逻辑（**有业务逻辑写在 OB 里 = 这个工程结构不好**，接手时要重点小心）

**产出：入口清单。**
```
OB「Main」        主循环   → 调用 FC1 / FB1@DB1 / FB2@DB2
OB「Startup」     启动     → 只做初始化赋值
OB「CyclicInt」   循环中断 → 调用 FB3@DB3（说明有需要固定周期的逻辑，通常是 PID 或积分）
```

### 2.2 第二层：画调用树（本阶段最有价值的产出）

从每个 OB 出发，逐层展开被调用的 FC/FB，直到叶子。

```
Main [OB]
├─ FcSafety [FC]                 ← 无实例，说明没有跨周期状态
├─ FbAxis [FB] @ InstFbAxis [DB]  ← 有背景 DB，说明有跨周期状态
│   └─ MC_Power [FB] @ 背景DB     ← 运动控制，必有工艺对象
└─ FbAutoSeq [FB] @ InstFbAutoSeq [DB]
    └─ 读写 DbTurn [全局DB]
```

**从调用树能直接读出三件事**（🥉 惯例，但很可靠）：
1. **FC 还是 FB** —— FB 有背景 DB，意味着有"记忆"（定时器、边沿、步号）；FC 没有 Static，它的状态一定挂在全局 DB 或 M 区
2. **哪个块是"公共块"** —— 被两处以上调用的块，改它风险最大（这条直接喂给工作流 B 的"不可碰清单"）
3. **有没有死代码** —— 软件树里有、但调用树里不出现的块。参考【本机 V21 · BlockLogic · `PMig_Msg_SysFctNotCalled`】：`The function {0} is never called.` / `函数 {0} 从未调用过。`（⚠️ 这条属**迁移场景**的消息，不是通用编译警告；此处只借它的语义，不要当成"编译会这样报"）

### 2.3 第三层：读单块 —— 用本助手的「解读程序」能力

这是产品已经做好、且竞品没有的能力（🥇 源码实读，`routes/tia-mcp.js` 的 `/describe-block` → MCP `DescribeBlockLogic`）。

**怎么点**：
```
左侧实时工程树 → 点一个程序块 → 出现「解读中…」
  → 右侧「上下文」面板切到【程序块逻辑】，显示：块名 / 路径 / 语言 / 可读逻辑
  → 面板底部有「导出 S7DCL」按钮（要看原始 XML 时用）
```

**它给你什么**（源码注释原文）：
> LAD 梯形图还原成布尔表达式，SCL/STL 读取其逻辑文本——电工看懂现场程序用。

**这是工作流 C 的主力工具**：LAD 是图，人眼一个网络一个网络挪很慢；还原成布尔表达式后，一屏能看十几个网络，**结构一眼就出来了**。

**读单块的四步**（🥉 惯例）：
1. 先看**接口**（IN/OUT/INOUT/STAT/TEMP）—— 接口就是这个块的"函数签名"，比正文更能说明它想干什么
2. 再看**网络注释** —— 有注释先信注释，但要交叉验证（注释和代码不一致是常态）
3. 再看**输出**（每个网络最后写了什么）—— 逆着读比顺着读快：先知道"这个网络在写谁"，再看"什么条件下写"
4. 最后才看条件细节

**读不动就导出 S7DCL 看原文**。特别是这几种情况必须看原文：
- 解读结果里出现了 `O` 块（并联）而你分不清支路 —— 看 `TemplateValue Name="Card"` 的数值和 `in1/in2/...` 接线
- 涉及定时器/计数器实例 —— 看 `<Instance Scope="...">` 挂在哪
- 涉及块调用 —— 看 `<Call>` 的结构（⚠️ 本项目对 `<Call>` 的**生成**能力为零，但**读**是没问题的，导出的就是权威写法）

## 阶段 3 · 变量表与注释还原

### 3.1 中文乱码：先判断，再决定值不值得救

🥇 **本机字节验算已证实的机理**：UTF-8 字节被按 GBK/CP936 解码（不是反过来）。

| 原文 | UTF-8 字节 | 按 GBK 解码 |
|---|---|---|
| 启动 | `E5 90 AF E5 8A A8` | `鍚姩` |
| 停止 | `E5 81 9C E6 AD A2` | `鍋滄` |
| 电机 | `E7 94 B5 E6 9C BA` | `鐢垫満` |
| 急停 | `E6 80 A5 E5 81 9C` | `鎬ュ仠` |
| 复位 | `E5 A4 8D E4 BD 8D` | `澶嶄綅` |
| 运行 | `E8 BF 90 E8 A1 8C` | `杩愯` |

⚠️ **`启动` 的乱码实际是 3 个字符，不是肉眼看到的 2 个**：`鍚`(U+935A) + U+E21A（GBK 私用区，不可渲染）+ `姩`(U+59E9)。

**对读程序的意义**：
- 看到 `鍚/鎬/鐢/澶/杩` 这类罕用字连续出现 → 立刻判定为"UTF-8 被 GBK 解码"，**照上表反查回原文**，读程序就通了
- 🥇 **不可回转**：`鍚姩` 按 GBK 编码只有 4 字节，与原始 6 字节不等长，字符串手术修不回来。**理解笔记里可以标注推定原文，但不要承诺"能修好变量名"**
- 做程序化识别时**不要匹配 `鍚姩` 字面量**（真实数据含不可见的 U+E21A，匹配不到），改为检测 U+E000–U+F8FF 私用区字符连续出现

### 3.2 没有注释时的推断纪律（🥉 惯例，但必须严格执行）

**允许推断，但推断必须打标。** 理解笔记里的每一条都要落在三档之一：

| 标记 | 含义 | 例子 |
|---|---|---|
| **【读到】** | 直接来自变量表注释 / 网络注释 / 解读结果 | `I0.1 停止按钮（变量表注释）` |
| **【推断】** | 从地址位置、命名习惯、逻辑形态推出 | `I0.1 在程序里以常开触点串在运行回路里 → 推断现场为常闭接线` |
| **【未知】** | 读不出来 | `M100.3 只在 FbAxis 里被写一次、无处被读 → 用途未知` |

**绝对禁止**：把【推断】写成【读到】。工作流 C 的产物会被拿去做工作流 B 的输入，一条假的"读到"能把改造带进沟里。

### 3.3 地址占用图（读程序的副产品，但极其有用）

按 I / Q / M / DB / T / C 分区，列出：已用地址 + 用途 + **空闲区间**。

这张图是工作流 B 阶段 2.1 的直接输入 —— **读懂了顺手就把改造的地基打好了**。

## 阶段 4 · 架构模式识别（把网络认成"积木"）

这是工作流 C 与"逐行翻译"的分水岭。目标不是把每个网络讲一遍，而是**认出作者用了哪几种通行模式**。识别特征来自《知识库_梯形图积木总表》（🥉 通用工程实践）：

| 模式 | 在解读结果里的识别特征 | 认出来之后要重点看什么 |
|---|---|---|
| **起保停（自锁）** | 输出**自己**出现在自己的条件里，且与启动信号并联（XML 侧 = `Part Name="O"` + `Card=2`，其中一路的操作数就是输出本身） | 停止信号是常开还是常闭串法；有没有第二处也写这个输出（双线圈） |
| **置位/复位式起保停** | 同一个输出既有 `SCoil` 又有 `RCoil` | S/R 的**先后顺序**——LAD 从上到下扫描，同一变量**后面的 S/R 覆盖前面的**（"谁在后面谁赢"） |
| **SR / RS 触发器** | 出现 `SR` / `RS` 盒子 | 🥈 官方原文（Table 7-12）：**`RS` 是 set dominant（S 优先）、`SR` 是 reset dominant（R 优先）** —— **名字最后一个字母 = 优先者，与多数人直觉相反**。读错这一条会把逻辑理解反 |
| **正反转互锁** | 两个输出，各自的条件里串着对方的常闭 | 有没有**硬件互锁**（程序互锁不够）；有没有换向过渡延时 |
| **星三角启动** | 一个 TON + 星/角两个接触器输出互锁 | 过渡断开时间；星角接触器的硬件互锁 |
| **步序状态机** | 一个 Int 变量被 `Eq` 反复比较、被 `Move` 赋值（SCL 侧是 `CASE #Step OF`） | ① 步号在**几个地方**被赋值（多于一处 = 隐患）② 每步有没有**超时监控** ③ 急停/报警时是否回零 |
| **步进/移位式流程** | 用一串位（M 或 DB 位）依次置位，前一位是后一位的条件 | 有没有"跳步"和"卡步"的保护；比 Int 步号法更难维护 |
| **GRAPH 顺序控制** | 块语言显示为 GRAPH | 它的 transition/interlock/supervision 三类网络官方明确"只能用 LAD/FBD 编"；S7-1200 不支持 GRAPH（🥈 四方交叉证实） |
| **报警锁存与汇总** | 一堆 `SCoil` 写报警位 + 一个大 `O` 块汇总 + 一个 `RCoil` 复位 | 复位条件里有没有串"故障已消失"（没串 = 按了没用还以为坏了）；瞬时故障会不会被漏掉 |
| **首出故障记忆** | 汇总位的常闭串在每一路报警的置位条件里 | 有没有正确阻断后续故障覆盖首出 |
| **模拟量标定** | `Convert` + `Sub` / `Mul` / `Div` 串成一条 | 量程系数是写死的还是走 DB；有没有除零保护 |
| **闪烁 / 报警灯** | 两个 TON 互相取反 | 周期是不是写死的 |
| **运动控制** | `MC_Power` / `MC_Home` / `MC_MoveJog` / `MC_MoveRelative` / `MC_MoveAbsolute` / `MC_Halt` / `MC_Reset` 等带背景 DB 的调用 | Axis 引脚接的是哪个工艺对象；使能与稳定延时；错误复位路径 |

### 4.1 认模式时最容易读错的四处（🥈 官方原文背书）

1. **SR / RS 反直觉** —— 见上表。这是高频错误源
2. **定时器线圈形式取不到 Q/ET** —— 🥈 手册 p.184："The -(TP)-, -(TON)-, -(TOF)-, and -(TONR)- timer coils **must be the last instruction in a LAD network.**" 所以线圈型定时器的 Q/ET 一定在**下一个网络**里以 `DB.timer.Q` / `.ET` 的形式被读。读程序时**别在同一个网络里找**
3. **运行中改 PT 无效** —— 🥈 Table 7-19："**Changing PT has no effect while the timer runs.**" 如果现场反馈"改了设定值没反应"，根因在这里，不是程序写错
4. **无符号计数器不回绕** —— 🥈 原文：无符号类型"count up to the range limit"。选 USInt 计到 255 就**停在上限**。"计数器卡住"的常见根因

### 4.2 一定要专门查一遍的两件事（编译器不管）

**① 双线圈**（🥇 双向确认 TIA 完全不警告：官方文档无相关警告文本，本机 `BlockLogic` 3256 条消息里搜 `coil|multiple assign|written more|assigned more` **零命中**）

根因：CPU 每周期从过程映像写物理点，程序内对同一个 Q 的多次写**后写覆盖先写**。危险在于**前面那段逻辑完全失效但看起来在工作**——在线监视还能看到能流。

查法：博途 **F11 交叉引用** / 交叉引用工具栏的 **Show overlapping access**（查 `M12.3 / MB12 / MW11 / MD10` 这类跨数据类型重叠）/ `程序信息 > 分配列表`。

**在理解笔记里，双线圈必须单列一节。** 这是接手别人程序时最容易被咬、也最难在现场复现的问题。

**② 边沿指令的 M_BIT 复用**（🥈 手册 §7.1.3 p.181 原文）
> "you should use a unique bit for each edge instruction, and you should not use this bit any other place in your program."

在被多次调用的 FB 里用 M 位 → 多个实例共用同一 M_BIT，边沿互相吞掉。FC 里没有 Static，同样串味。**读程序时看到边沿指令，顺手查一下它的存储位有没有被别处用。**

⚠️ **一处未消解的矛盾（诚实标注）**：本机 DLL 有一条 `The edge evaluation instructions can only access the parameters defined in the InOut or Temp sections of the block interface.` / `中指令的边沿评估只能访问块接口 InOut 或 Temp 部分中所定义的参数。` —— 与手册"应避免 temporary memory 作 M_BIT"表面冲突。两者大概率讲的是不同对象（**指令操作数可位于哪些接口段** vs **M_BIT 存储位该放哪**），**但未证实**，读程序时不要拿它下结论。

## 阶段 5 · 定向追查：某个输出为什么动 / 为什么不动

客户最常问的其实不是"这个程序在干什么"，而是"**为什么这个气缸不出来**"。

### 5.1 首选：`TraceTagCause`（🥈 官方工具说明，产品可达）

```
POST /api/tia/mcp/call
{ "name": "TraceTagCause", "args": { "blockScope": "<限定块，可选，更快>" } }
```

官方描述原文（要点）：
> Answer 'why is tag X this value / what sets it' by **static analysis of the OFFLINE project**. Read-only: exports code blocks to SimaticML and finds **every network that WRITES the tag** (LAD coils S/R/=, or StructuredText ':=' assignments) plus the **gating condition operands** in those networks. Cross-reference service is not needed. … NOTE: block export needs the project **OFFLINE**.

**这个工具正好覆盖工作流 C 最难的一环**：它把"谁写了这个位"和"写的时候门槛条件是什么"一次给出，**而且不依赖交叉引用服务**（`GetCrossReferences` 是 best-effort，可能拿不到）。

配套：`TraceTagCauseLive` 可以把返回的 gatingConditions 现场读活值，看**当前是哪个条件在压着**。⚠️ 活值读取属在线操作，**必须先向用户说明并取得同意**，且与阶段 0.2 的"离线才能导出"冲突——**顺序是：先离线做 `TraceTagCause`，再在线读活值**。

### 5.2 兜底：人工三件套

`F11 交叉引用` → `Show overlapping access` → `程序信息 > 分配列表`。工具拿不到时必须回退到这三样，**不许因为工具没返回就下"没人写它"的结论**。
